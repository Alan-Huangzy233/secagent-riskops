# SSH 认证告警

中控对已接收的 SSH 日志按日志时间评估规则，识别密集失败、较长时间内的低频尝试、多账号尝试、跨来源尝试，以及多次失败后成功。规则只生成待人工核查的告警，不执行封禁或其他远程操作。

## 默认规则

| 规则 ID | 控制台名称 | 关联条件 | 默认阈值 |
| --- | --- | --- | --- |
| `burst` | 短时密集失败 | 同一来源、同一对端 IP | 5 分钟内至少 3 条失败日志 |
| `slow_scan` | 慢速扫描 | 同一来源、同一对端 IP | 2 小时内至少 12 条失败日志 |
| `multi_account` | 多账号尝试 | 同一来源、同一对端 IP | 2 小时内至少 6 条失败日志，涉及至少 3 个不同的非空账号 |
| `cross_source` | 跨服务器尝试 | 同一对端 IP，至少 2 个不同来源 | 30 分钟内至少 6 条失败日志 |
| `success_after_failures` | 多次失败后成功 | 同一来源、同一对端 IP | 一条认证成功日志之前的 30 分钟内至少 3 条失败日志 |

失败日志包括 `auth_failure`、`invalid_user`、`preauth_abort`。认证成功采用 `auth_success`。空账号不参与不同账号数计算。规则窗口可以跨采集批次，因此不要求某次上传中同时包含全部匹配记录。

窗口下界包含端点；“失败后成功”要求成功时间严格晚于相应失败时间。共享证据的多个达标窗口可以合并为一个事件，因此整个事件的时间跨度可能超过单条规则窗口。重复上报的同一来源、同一日志 ID 不会再次计数，跨来源相同日志 ID 则保留各自证据。不同来源的时间同步会影响跨服务器关联。

计数单位是日志记录。一条 SSH 连接可能产生“无效账号”和“认证前断开”等多条记录，所以 `failure_count` 不能解释为独立登录次数、连接数或攻击者数量。跨来源关联以中控配置的稳定 `source_id` 区分资产；同一个 IP 也可能属于 NAT、代理或共享出口，不能据此确认是同一个人。失败后成功意味着应核查成功登录，不能单独证明账号已失陷。

## 告警和页面

新接收的日志自动参加规则评估。同一组关联证据可以命中多个规则，页面显示命中规则、全部关联服务器和来源 ID、失败日志数、成功日志数及非空账号数。点击记录查看规则版本、窗口、原因、账号和原始证据。筛选一个来源时，应包含涉及该来源的跨服务器告警。

API 保留原有 `source_id`、`hostname` 和 `failure_count` 字段供旧调用者使用。其中单个来源字段表示告警的锚点；需要完整关联范围的调用者应读取 `source_ids`、`hostnames`。新增的 `rules` 包含 `rule_id`、`rule_version`、`window_seconds` 和 `reason`；`success_count`、`username_count`、`usernames` 描述告警证据中的认证结果和账号。

页面兼容尚无上述扩展字段的旧记录，并显示“登录失败（旧版记录）”。刷新间隔、手动刷新、分页和 IP 查询保持原有行为。刷新不会删除数据库里的告警；日志和证据仍受保留策略约束。

## 处置状态

每条告警有独立于检测状态的处置状态，默认列表只显示“待处理”；页面顶部可切换。

| 状态 | 含义 |
| --- | --- |
| `pending` 待处理 | 新产生的告警，或已处理后再次出现新证据的告警 |
| `acknowledged` 已知晓 | 操作员已知悉但尚未采取措施；之后的新证据不改变此状态 |
| `resolved` 已处理 | 已封禁或人工确认处理完毕 |

操作员可以执行的转换是 待处理 → 已知晓 / 已处理，已知晓 → 已处理 / 待处理，已处理 → 待处理；
其他组合会被拒绝而不是强制覆盖。三种自动转换由系统记录：

- **封禁核实**：某个 IP 在告警涉及的每一个来源上都存在已核实、未到期的 SSH 或 TCP 封禁时，
  该 IP 的未处理告警标为已处理，记录引用操作任务 ID 与操作原因。只封禁部分来源、仅封 UDP
  或解封不会改变处置状态。
- **新证据**：已处理的告警若关联到日志时间晚于处理时间的新证据，则回到待处理。晚到的历史
  记录、历史重建（`rebuild_ssh_detections.py`）加入的旧证据不会重新打开告警。
- **合并**：两条告警合并时保留处理程度较低的状态，避免未处理的活动被已处理的身份掩盖。

每次转换写入 `incident_triage_log`（时间、操作者、前后状态、原因、备注、引用），详情接口的
`triage_log` 返回最近 50 条。列表和详情返回 `triage_status`、`triage_updated_at`；
`/api/incidents` 与 `/api/dashboard` 接受 `triage` / `incident_triage`
（`pending`、`acknowledged`、`resolved`、`all`）并返回 `triage_counts`；概览的 `triage_counts`
给出全局计数。修改状态使用 `POST /api/incidents/triage`，请求体为 `incident_ids`（1–100 个）、
`state` 和可选 `note`（不超过 300 字），与封禁接口一样要求操作员认证、CSRF 头和同源请求；
结果逐条给出 `changed`、`unchanged`、`invalid` 或 `missing`。

处置数据保存在附加表中；回退到没有此功能的版本时旧程序会忽略这些表，重新升级后状态仍在。
处置状态只是中控的记录，不会向来源发送任何命令，也不影响规则评估。

## 重新评估已有日志

部署新规则不会隐式重建整份历史数据。需要处理保留期内已有日志时，使用程序附带的本地重建命令。先确定配置中的数据库路径，再预览变更：

```sh
python scripts/rebuild_ssh_detections.py \
  --database /var/lib/secagent-riskops/telemetry.sqlite3 \
  --dry-run
```

预览期间也应暂停数据库写入，或先制作 SQLite 一致副本并对副本预览；如果并发写入改变数据，预览会拒绝宣称完整性验证成功。应用前进入维护窗口，停止 API、collector 和其他会写入该数据库的进程。确认预览后显式应用，并指定受限的本地备份目录：

```sh
python scripts/rebuild_ssh_detections.py \
  --database /var/lib/secagent-riskops/telemetry.sqlite3 \
  --apply \
  --backup-directory /var/backups/secagent-riskops
```

上述路径只是部署示例，应替换为实际配置。重建后核对规则分布、证据和采集状态，再恢复写入进程。重建只能使用当前数据库中仍保留的日志，不能补回未采集或已清理的证据。备份和预览输出属于运行数据，不应提交到代码仓库。

## 使用边界

这些默认阈值是初始检测策略。合法管理员反复输入错误密码、自动任务使用过期凭证、共享出口等情况也可能触发告警。它们不覆盖所有频率更低的尝试，也不能仅凭 SSH 日志观察出站连接、进程网络活动或完整网络流量。应结合账号、来源资产、时间范围及原始证据确认事件。
