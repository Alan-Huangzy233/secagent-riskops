# Joint AI evidence contract and local preview

[Issue #148](https://github.com/Alan-Huangzy233/secagent-riskops/issues/148)
extends advisory review to retained network and SSH evidence. The contract defines a bounded summary and deterministic response checks.
An operator-only console preview now reads saved observations through that
contract. It adds no queue, provider transport, automatic analysis or response action.

The existing SSH/HTTP dossier, provider fingerprints and manual SSH workflow
retain their versions and behavior. A joint dossier carries a distinct
`dossier_version: "joint-v1"`; the existing provider adapter rejects it. Existing
permission to send SSH summaries does not authorize network or joint summaries.

## Inputs and version binding

`telemetry.joint_ai_summary.build()` accepts a `ValidatedRead`, its `CaseScope`,
an explicit `SnapshotContext`, and a private `Aliases` key. It revalidates the
whole observation, including the enrolled mapping and retained references,
before constructing the summary. A list row or one timeline page cannot
substitute for this input.

`SnapshotContext` identifies the derived store, restore/query epoch, exact saved
case revision and current revision. It separately records refresh state/error,
assessed freshness and pending restore revalidation. These are trusted
server-side inputs, not values accepted from a browser or generated by a model.
Freshness must be assessed explicitly: a previous successful refresh does not
by itself mean a case is current. The pure builder cannot discover omitted
source records, verify supplied context against a database, or authenticate a
supplied observation.

The summary revision binds the complete projection hash, mapping/policy scope,
store and restore epoch, saved/current revisions, freshness context, summary
policy and record cap. New SSH evidence can therefore invalidate a summary even
when the network revision stays unchanged or the new record falls outside the
sample. Routine read timestamps do not change an otherwise identical summary
revision. Hashes and keyed aliases are identifiers, not signatures.

## Saved-case preview

`GET /api/joint/cases/{case_id}/ai/preview?revision=N` requires operator
credentials and an explicit saved revision. It accepts no browser-supplied
dossier or freshness assertions. The route reuses the service's already loaded
private alias key; absent alias configuration returns a fixed unavailable error.
It does not initialize storage, inspect model budgets, create jobs or call a model.
Successful responses use `Cache-Control: no-store`.

`JointCaseQuery.ai_snapshot()` reads the full validated saved observation,
current registration, store identity, query epoch and query status in one SQLite
read transaction. The adapter evaluates the separate refresh checkpoint at a
fixed capture time, builds the summary, then rereads and compares the full
snapshot and refresh status. A detected change returns `joint_preview_changed`
so the operator can retry. This optimistic check is not a cross-file atomic
snapshot; the response describes its capture time, not a promise of continuing
freshness. A future submission and result display must revalidate independently.

Only a ready store, fresh error-free registration, and idle successful scheduler
checkpoint within its age limit can establish `current`. Missing, disabled,
unreadable, mismatched or future-dated checkpoints cannot establish freshness.
Historical revisions, pending restore revalidation, source errors and expired
observations remain explicit. Preview does not refresh evidence from source
stores or fill gaps from the latest logs.

The response adds `preview` metadata with `mode: "local"`, `external_calls: false`
and `captured_at`. The console's **AI摘要** tab requests it only after an explicit
button click, shows paginated aliased evidence and expandable local references,
and clears results when leaving the tab, changing case/revision or closing the
details. The preview grants no permission to transmit its contents.

## Output boundary

The builder returns a local envelope marked
`dossier_version: "joint-local-envelope-v1"`, containing three separate objects:

| Object | Purpose |
| --- | --- |
| `case` | Strict aliased dossier; candidate input for a future, separately approved transport |
| `local_refs` | Original source/event identities and retained incident references for each included event |
| `meta` | Local store/revision binding, projection hash, time origin and sampling policy |

Only `case` is a candidate for an outbound request. The complete wrapper must
never be sent to a model. Its envelope marker also makes the existing provider
adapter reject the whole wrapper before request rendering, preventing legacy
protocol fallback if a caller accidentally passes the local object.

The dossier allowlist contains:

- Stable keyed aliases for case, revision, mapped asset, source, observed peer,
  destination, account and evidence identity. Event aliases include domain,
  source and original ID, so cross-domain names do not merge evidence. A missing
  SSH account remains explicitly absent.
- Integer microsecond offsets from the association window start when available,
  plus the window duration. Without a valid window, offsets describe only order
  relative to the first retained record.
- Normalized local-input TCP observations and destination ports, plus the
  retained SSH event type. Pre-authentication aborts and disconnects retain their
  distinct meaning.
- Association and review state, domain-specific observed/retained/included
  counts, separate completeness flags and fixed limitation codes.

Raw IPs, source/asset names, accounts, event and incident IDs, boot/profile
identities, absolute timestamps, arbitrary coverage-code text, logs, paths,
headers and database locations are excluded from `case`. Aliases preserve
equality within the key's scope; this is pseudonymization, not anonymity.
Destination ports and relative timing may still reveal behavior and require an
explicit field-policy review before any future live transport.

## Bounds and missing evidence

The builder includes at most 40 events and 64 KiB of dossier JSON. Private
references, metadata and envelope marker together are capped at 256 KiB. Callers can lower these
limits. Byte overflow returns a fixed failure instead of discarding references.
Existing retained-observation byte and row limits also remain in force.

Sampling alternates between chronological network and SSH prefixes, then returns
selected records chronologically. Both domains remain represented when present
and the cap permits it; a cap of one may include only network evidence. This is
not severity ranking or a guarantee that a late success is included. An omitted
success is never evidence of failure or safety. Original reference ownership is
preserved for every included event.

`input_complete` describes supplied projection inputs. `timeline_complete`
describes whether the saved timeline contains all observed records.
`summary_complete` describes whether all saved records fit this smaller summary.
None establishes collection coverage: `coverage_complete` remains `null`.
Counts are observation lower bounds, not the full extent of an attack.

Limitations always preserve unknown source coverage and clock alignment,
shared-IP ambiguity, retained-incident scope and non-atomic source reads.
Additional gap, temporal and truncation flags remain explicit. An unmatched
case means no matching retained SSH evidence in this scope, not no SSH activity.

## Advisory response checks

`agents.joint_triage.validate(text, case)` returns a safe advisory result plus
review details. Its independent `joint-validator-v1` policy permits only
`escalate` and `abstain`. Dismissal, blocking and action fields are unsupported.

Responses must name the exact dossier revision and cite included event aliases.
Unknown fields, duplicate JSON keys, invalid types, oversized output, invented
references and unsupported claims produce an abstaining review result. Errors
use fixed codes instead of echoing rejected values. Historical, stale,
unavailable, unknown or revalidation-pending observations cannot support a
current escalation. An association marked `stale` or `retracted` requires
abstention even if its `review_state` is `current`. A changed dossier revision
invalidates a previous response.

| Typed claim | Required cited evidence |
| --- | --- |
| `network_observed` | One or more local-input TCP observations only; different network groups may be cited without asserting a shared port group |
| `multiple_destination_ports` | Only network records with identical `source`, `destination`, `asset` and `peer`, containing at least two distinct `dst_port` values |
| `ssh_failure_observed` | Only SSH records of type `auth_failure`, `ssh_failure` or `invalid_user`; pre-authentication aborts and disconnects do not qualify |
| `authentication_succeeded` | Only SSH records of type `auth_success` or `ssh_success`, each with an account; this does not prove exploitation |
| `ssh_network_associated` | Both domains for the same mapped asset/peer, with association state `linked` or `partial`, within a usable window and without temporal uncertainty blockers |

Each claim has its own supporting event list. Every cited record must satisfy
that claim's requirements; a valid subset does not make unrelated appended
records valid. For a multiple-port claim, `source` is the collecting source alias,
while `peer` is the observed remote-peer alias. Matching `peer` alone does not
make different `source` or `destination` values one port group. Select records
from one qualifying group and keep other groups in separate claims. Repeated
ports within a group are allowed when that same group still contains at least
two distinct ports; single-port groups cannot be combined to qualify.

The current summary builder emits network observations from one source and
destination group. The dossier contract also accepts multiple groups, so claim
checks retain the same boundaries for alternate or future dossier producers.
A mixed-group synthetic dossier exercises this defensive contract; it does not
represent the current summary builder's usual output.

The prompt states each typed claim's evidence requirements using shared immutable
port-group fields, SSH event types and association gates. The baseline
`clock_alignment_unknown` and `source_coverage_unknown` limitations preserve
uncertainty but do not themselves prohibit a scoped association claim. The
association still requires the states and usable temporal relation above, and
must exclude `temporal_association_unavailable`, `network_anchor_span_exceeded`
and `network_clock_unverifiable`.

Responses must copy event IDs and the revision exactly. Rationale should match
the typed claims and their cited evidence. Exact counts of network observations,
SSH failures, SSH successes or distinct ports refer only to the matching cited
records, not unrelated record types or uncited observations. Included records
and retained counts never establish a complete attack count or coverage.
These instructions do not turn narrative into a deterministically verified fact.

Escalation needs a supported positive claim. Partial evidence can support a
positive observation, but cannot establish absence, authorization or safety.
Claim checks also apply to an abstaining response. A stale or retracted
association may retain supported network or SSH observations, but cannot support
an `ssh_network_associated` claim. The prompt and validator share their state
and temporal limitation gates; these requirements do not change the validator
version or its accepted response contract.
TCP observations do not establish a completed connection, open service or
compromise. Matching peer/time does not identify an attacker or prove causality.

Rationale text and ATT&CK suggestions remain unverified model proposals. The
effective result uses fixed review wording, while the original proposal stays
separate for human judgement. Passing typed checks is not measured model accuracy
or proof that the narrative is correct.

## Remaining #148 work

Follow-up increments must add manual submission and result history to the local
preview, with job persistence and stale-result checks, recorded/fake provider
integration and existing budget/retry guarantees. Network field policy,
provider, budget and rollout approval precede live calls. Automatic analysis and
automatic response remain separate work.

Focused local checks use authored synthetic evidence and temporary stores:

```sh
python -m pytest backend/tests/test_joint_ai_summary.py backend/tests/test_joint_triage.py
```

Operational evidence, local check results and deployment configuration are not
part of this contract or its repository artifacts.
